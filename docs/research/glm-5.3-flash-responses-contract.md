# Z.AI GLM-5.3-Flash 与 Codex Responses 工具流契约

研究日期：2026-09-28。目标是为[适配决策地图](https://github.com/immorcoding/codex-multiprovider/issues/1)提供接口证据；未使用账号、密钥或在线模型调用。本笔记针对 Codex 官方 `rust-v0.158.0` 标签，不把本地 `E:\Projects\codex` 的旧 `multiprovider-routing` 分支当作新版基线。以下“文档确认”仅表示所引公开文档的陈述，“源码确认”表示该标签客户端的行为；二者的组合不等于端到端兼容已验证。

## 官方文档内的界限与矛盾

- [Z.AI Codex 指南](https://docs.z.ai/devpack/tool/codex)的目录示例是 `glm-5.3`，不是 Flash；[Flash 模型页](https://docs.z.ai/guides/vlm/glm-5.3-flash)确认 Flash 在 Coding Plan，因而“把官方示例 slug 换成 Flash”是合理候选配置，**不是该组合流式工具流通过的证据**。
- Chat Completion 参考页的枚举列表尚未包含 `glm-5.3-flash`，但专门的模型页明确给出其编码；以模型页作编码依据，实际请求以服务返回为准。[Chat Completion 参考](https://docs.z.ai/api-reference/llm/chat-completion)、[模型页](https://docs.z.ai/guides/vlm/glm-5.3-flash)
- Z.AI 的 [Tool Streaming Output](https://docs.z.ai/guides/capabilities/stream-tool)文本有“limited to `glm-5`”一句，而同页示例使用 `glm-5.3`，模型页又推荐 `tool_stream: true`。这不构成 Flash 的 Responses 工具增量事件保证；勿把 Chat 的 `tool_stream` 直接塞进 Responses 请求。[Flash 模型页](https://docs.z.ai/guides/vlm/glm-5.3-flash)

## 建议的验收探针（需测试账号，尚未执行）

1. 使用 Coding Plan 对应 Key，直接 POST `/api/v1/responses`：最小文本请求及 Codex 原样请求各一次；记录状态码、拒绝的字段、响应 `Content-Type`、脱敏 SSE 事件类型。不要在日志中保存 Authorization、完整对话或推理内容。
2. 强制单个 function 工具：检查 `response.output_item.done.item` 的 `type/name/arguments/call_id`，再以相同 `call_id` 回送结果，直至 `response.completed`；同时跑并行调用和空／错误工具输出。比较 `reasoning.effort` 三档与思考项回传。
3. 冷启动、多轮长对话、重试和中断恢复；检验 `store: false` 的完整历史重放、reasoning item 兼容、是否存在必须维持的服务端状态。通过 HTTP 再测 SDK 调用；WebSocket `previous_response_id` 另列可选范围，不应误作 HTTP 必需。
4. 使用无真实密钥的 mock SSE 回放固定契约，再决定直连还是最小转换代理。若服务只支持 Chat Completion，不应把 `choices[].delta` 直接交给 Codex，必须明确设计完整双向协议转换与错误／工具／续轮语义。
